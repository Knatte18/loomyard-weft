# Edit-loop watch counts only edits that return a file to earlier content

The edit-loop watch counted every edit of a file.
A fixer applying several review findings to one file, or a writer whose whole output is one document, edits that file many times by design,
so the watch reported ordinary work as a loop: `gate-test-map-mode`'s Plan-Burler-Fix agent and `codex-standing-instructions`' Code-Burler-Fix agent each drew notices while making progress.
The hub's shuttle config then set `edit_loop_edits: 0` to silence the noise.

The watch now counts only an edit that undoes or repeats an earlier one: an edit that leaves the file with content an earlier edit of it left.

## What changes

- The Claude edit hook (`internal/shuttleengine/claudeengine/editrecord.go`) adds lym's own `content_hash` to each edit record:
  the SHA-256 of the edited file's content as the hook reads it after the edit.
  The record still holds no edit text and no file content.
  A file the hook cannot read is recorded with no hash, and that edit never counts.
- `ParseSessionSignals` reads the hash into the new `SessionSignal.ContentHash`.
- `internal/shuttleengine/editloop.go` keeps, per agent and file, the content each edit left and the edits that repeated one.
  An edit is a repeat when its hash matches content an earlier edit of the same file by the same agent left within `edit_loop_window_s`.
  Once the repeats within the window reach `edit_loop_edits`, the parent gets one notice and that file's history restarts.
  A back-and-forth edit, the same `old_string` swapped to and fro, or a reverted fix applied again, all return the file to an earlier content.
  Edits that make progress leave new content each time and never count.
- The notice now says the agent edited the file back to content it held earlier N times within the window.
- `edit_loop_edits` now counts repeats, and its template default drops from 4 to 3:
  a two-state flip draws the notice on its fifth edit.
- A config reinterpretation, `shuttle-edit-loop-repeats` (`shuttleengine.DropEditLoopEdits`, registered on the shuttle module in `configreg`),
  drops a hub's `edit_loop_edits` once when it is 0 or null, so the template's count applies.
  It mails the hub's orch one line naming `lym config shuttle --layer default` as the way to set another count.
  This turns the watch back on for a hub that set 0 while the notices were noise, with no hand edit of the hub file.
  Any other value stays in the file and is flagged to the hub's orch, with the way to set a count of repeats.

## Design decisions

- Repeats are told by the file's content hash after the edit, not by comparing `old_string` and `new_string`.
  The hash covers `Write` calls as well as `Edit` calls, and it catches any return to an earlier state, however the agent got there.
  It cannot see the content before an agent's first edit, so a single undo of that first edit is not a repeat;
  a loop that keeps going is caught from its third edit on.
- Repeats count per agent and file, as edits did, so a session and its subagents never add up to one loop.
- No role is exempted and no per-role count is added: with progress edits no longer counted, a fixer or one-document writer needs no special case.
- The old count of every edit has no equivalent count of repeats, so the reinterpretation converts no value.
  A 0 meant off before and after, so dropping it carries no meaning across and lets the template's count apply.
  Any other count is the hub's own choice, which only the hub can restate, so it is flagged and left in place.
