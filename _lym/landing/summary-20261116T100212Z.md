# Orch sessions start with remote control on, and an RC button turns it on

Every orch session lym launches or resumes now starts with Claude Code's remote control on, under a name that tells machines and hubs apart, so a context cycle or a fresh orch session no longer drops the phone link.
A per-hub switch in orch.yaml turns this off.
An `RC` button on the orch session's status bar turns remote control on in a session running without it.

## What changes

- **orch.yaml.**
  Two new keys:
  `remote_control: true` and `remote_control_name: "{machine}::{name}"`.
  The name template fills `{machine}` (this machine's name), `{hub}` (the hub's shortname), `{role}` (the orch strand's role) and `{name}` (its full agent name) in one pass; other brace text stays literal.
  The default renders the cross-machine address creel already uses, such as `neve::ly:orch`, and a test pins that it equals `agentname.FormatMachineAddress`.
  `LoadConfig` refuses a name holding a control character, and an empty name while the switch is on.
  Both keys are `CategoryNone`.
- **Launch.**
  `orchcli.startOrch` forms the name from the strand name the launch takes:
  the listed strand's, or else the fixed `<shortname>:orch` or `<shortname>:<slug>:orch`.
  It passes the name on the orch spec's new `shuttleengine.Spec.RemoteControlName`.
  The claude engine puts `--remote-control <name>` on both the launch line and the resume line, so a session reed revives keeps it.
  Only the orch spec sets the field, so writers, reviewers and task sessions get no flag.
  A Codex orch gets nothing:
  the launch checks that the orch's engine implements the new `shuttleengine.RemoteController` capability, and the Codex engine does not.
  A name that cannot be formed, for example because the machine name is unreadable, is logged at Warn, and the session launches without remote control rather than failing the bring-up.
- **The record behind the button's colour.**
  `orchengine.RemoteControlRecord`, at `.lym/orch/remote-control.json`, holds the strand guid and whether lym turned remote control on.
  It sits in a file of its own because the watcher saves the whole orch state from a copy loaded at tick start, which would overwrite a field a click had set.
- **The RC button.**
  Reed draws `RC` on line 3 between the slack and away toggles.
  It shows only while the session's worktree records an orch strand and the remote-control record names that strand.
  It is lit green while that record reads on.
  It reads its state from a `#()` job of its own, `lym orch rc-bar --dir <run dir>`, pinned like the Slack state job.
  That verb skips the orch wiring, which would refuse a task pair's session.
  A click runs `lym orch rc-on`.
  That verb queues creel's new `remote-control` command into the worktree's live orch strand, signed as the `REMOTECONTROL` program, under the same name a launch would pass, whatever the switch says.
  It then records the strand on and redraws the clicking client's bar, showing a refusal there first.
- **Creel and shuttle.**
  Creel's closed command set gains `remote-control`, whose argument is the one-line session name.
  Creel's delivery runs it through `Runner.TurnOnRemoteControl`.
  That method types the engine's `RemoteControlSequence`, `/remote-control <name>` and Enter for Claude, through the guarded send path.
  It types nothing for an engine without the capability.
  So text reaches the orch pane only through creel, as PATTERN-reed-panes requires.

## Design decisions

- **The colour shows what lym last set.**
  Claude Code exposes no reading of whether remote control is on, in the transcript, the status-line payload or its session files, that lym could read reliably.
  So, as the board entry's fallback allows, the record holds what a launch or a click set.
  A session whose remote control the operator turned off inside Claude Code still shows lit until the next launch.
  The orch and reed package docs and the `rc-bar` help state this.
- **A click on a lit button refuses and sends nothing.**
  While the record reads on for the live strand, the refusal's way forward names `/remote-control` typed by hand in the orch pane,
  which is how to recover a session whose remote control was turned off inside Claude Code.
- **A start adopting an already-running strand the record does not name records it off.**
  The RC button then shows dim, and a click turns remote control on.
- **The click lights the button once creel accepts the command.**
  The record is written when the inject is queued, so a busy orch shows lit before the command is typed at its next idle.
- **A separate state job** rather than one shared with the Slack toggles.
  It reuses the Slack pattern exactly, at the cost of one more `lym` process per session per redraw interval.
- `orchroute.FixedStrandName` is extracted from `StrandOf` so the launch and creel addressing share one naming rule.
- `reedengine.switchBindingCommandsLocked` became `bindingLinesLocked`, which returns a struct, since eight positional return values were unreadable.

## Open risks

- The button needs the session's `@lym_button_dir`, which reed sets only when the session renders action-row buttons.
  The Slack toggle has the same dependency.
- An orch on an engine with no remote control, such as Codex, writes no record, so no RC button is drawn for it.

## Tests

New and changed rows cover:

- the claude launch and resume lines with the flag;
- `RemoteControlSequence`;
- creel's command validation and delivery mapping;
- orch.yaml's switch, name refusals and the name template;
- the remote-control record;
- the launch passing and recording the name, which is empty with the switch off and on an engine without the capability;
- the click's queue, record and refusals;
- the button's state word;
- the bar format, the click binding branch, the pinned lines and the composed `rc-on` and `rc-bar` lines.
