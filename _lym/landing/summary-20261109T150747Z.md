# Title every console window `<hub>: <P#>: <T#>: <slug>`

With several hubs open on one machine, the operator could not tell which window belonged to which hub and project.
VS Code's `window.title` was the upper-cased shortname and the slug, and a terminal window from `lym reed window` was titled with the bare slug or `T4: <slug>`.
Now every console window, VS Code or desktop terminal, takes one title form, read from the board when the window opens:

| What | VS Code | Terminal window |
|---|---|---|
| Task in project P3 | `ly: P3: T7: gate-shard-slow-package` | same |
| Task with no project | `ly: T12: adopt-fix-root-t1` | same |
| Task under beam P2 | `mo: P2: T4: wellbore-build-cost` | same |
| Beam P2 itself | `mo: P2: beam` | `mo: P2: orch` |
| Prime | `ly: prime` | `ly: orch` |

A part that does not exist is left out, and the shortname is lower case, as `lym creel hubs` prints it.
A workspace file keeps its suffix: `ly: loomyard workspace`, `ly: <beam> workspace`.

## What changed

- `internal/consoletitle` is a new stdlib-only leaf holding the one function that joins a title, `Title(shortname, projectHandle, ownHandle, name)`, plus `Workspace` and the `prime`, `beam` and `orch` labels.
  It is a leaf so `fabricengine`, which may not import the board, forms the workspace title with the same function.
  `PATTERN-leaf-packages` gains its section, and a leaf enforcement test pins it.
- `boardengine.IDEWindowTitle` and `boardengine.TerminalWindowTitle` resolve a worktree's parts.
  They read the hub shortname and the board at the call.
  `<P#>` is the handle of the nearest open beam above the entry (`ParentBeam`), else of its `project`.
  An unreadable board is logged at Warn and leaves out every handle; a title never fails its caller.
- The places that formed a console title now call it:
  - `ideengine.lookFor`, behind `lym ide seed` and `lym ide spawn`;
  - `fabricengine.workspaceWindowTitle`, for the hub and beam workspace files;
  - `lym reed window`'s default title, when no `--title` is given;
  - batten's `{title}` placeholder, which the default `open_window_command` already passes.
- The reed status-bar `terminal` buttons in the task, beam and prime groups drop `--title {slug}`, so `lym reed window` forms the title itself.

## Design decisions

- **Which window is "Prime" and which is "Orch".**
  The board entry's table names both a `Prime` and an `Orch` row for the same worktree.
  I read the prime's VS Code window as `ly: prime` and the terminal window on the prime's reed session, where the orch runs, as `ly: orch`.
  In the same way, a beam's VS Code window reads `<P#>: beam` and its terminal window `<P#>: orch`.
  A task's two windows share one title.
- **The `runs` window keeps its name; the loom status window takes the console title.**
  The entry says the `runs` strand and the operator shell get no title of their own.
  So the `runs` window (`beam: prime`, `P1: beam: <slug>`) keeps its existing name, which `boardengine.TitleWithHandle` still forms.
  The loom status window is a window of a task's or beam's own session, not the `runs` strand, so `boardengine.RecipeWindowTitle` names it with the console title, the recipe standing where the slug does: `ly: P3: T4: tapestry`.
- **`lym reed window` forms its own default title** instead of each caller passing one.
  The verb resolves the worktree that holds the told directory, then the prime name through `fabricengine.PrimeName`.
  A directory in no worktree keeps its base name.
  A `--title` still wins.
  A hub that wrote its own `buttons` group into a layer keeps any `--title {slug}` it holds, and so does a hub that set `open_window_command` with `{slug}` in place of `{title}`.
  No config value changes meaning, so no reinterpretation ships.
- **No part of lym reads a title back.**
  I searched for readers of `window.title`, terminal window titles and the `{title}` value and found none.
  `desktop.window_command` gets the window's directory, not its title.
  reed's window ordering reads the strands' display titles, which now carry the shortname for the status window; it orders by anchor and order, so the new title changes no order.

## Tests

- `consoletitle`: `TestTitle` and `TestWorkspace` pin every form, the lowered shortname and the left-out parts.
- `boardengine`: `TestWindowTitles` pins both titles for the prime, a beam, and a task in a project, in no project and under a beam.
  It also pins that a beam above a project wins, and covers a worktree off the board, no shortname, an unreadable board and no board.
- `ideengine.TestLookFor` pins the new VS Code titles, with handles added to its board fixture.
  Its integration tests, and `fabricengine`'s workspace integration test, pin the lower-cased shortname.
  `TestRecipeWindowTitle` pins the status window's title, and `loomcli`'s `TestStatusWindowTitle` pins it with the shortname and project handle.
- `reedcli`'s window test pins that a missing `--title` takes the formed title through a new `windowTitle` seam.
  A tier 1 test runs `terminalWindowTitle` against a hub fixture and a directory in no worktree.
- `reedengine`'s config test pins the shipped buttons without `--title {slug}`.
