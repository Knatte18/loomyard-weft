### [MEDIUM] D4's fence length can fall below three backticks

**Location:** `_lym/discussion/decision-record.md` D4, the fence form, and the D4 acceptance row.

**Issue:** D4 sets the outer fence to "one longer than the longest backtick run in the body" and sets no minimum.
A body with no backticks gets a one-backtick fence.
A body that uses only inline code gets a two-backtick fence.
Neither one opens a fence, either in CommonMark or in `fencedLines` (`internal/discussionparser/append.go:354`, which needs three).
This task's own board body (`lym board get '{"slug":"run-verbs-shared"}' --body`) has only single-backtick spans, so its `## Seen`, `## Open` and other H2s would become sections of the record.
A body `## Decisions` would capture `decision add`'s insertion through `decisionsInsertOffset`.
D4's Bound says an empty body writes an "empty fenced block", and under this rule that block is a one-backtick line, which is not a fence.
Found also by the walkthrough lens and by the handler.

### [MEDIUM] D6 leaves the no-parent `Decision for <slug>:` note undefined

**Location:** `_lym/discussion/decision-record.md` D6, and the answer key D7 sets.

**Issue:** The writer still reads `Decision for <slug>:` notes (D6), but it may never edit the record, and with no parent nobody can run `lym loom decision add`.
Today's stencil handles exactly this case: when a note answers, the writer goes ahead, and with no parent it writes the note's answer into the record (`contracts/stencils/darn/darn-template-write.md:42`, `:48-50`).
D6 removes that path and puts nothing in its place.
If the writer follows the note, the Code-Review perch reviews the change against a record that lacks the answer, because D7 makes the record its whole answer key.
If the writer stops, the record does not say the halt carries the note's answer.
The focus directive asks for exactly this no-parent note case.
Round 1's F6 raised the same defect.
Its fix made the halt name `lym loom decision add` then `lym loom resume`, but D6 still has the writer read these notes and still does not say what it does when a note already answers, so the defect is only half fixed.
Found also by the walkthrough lens.

### [MEDIUM] D13 drops a tuned hub-base key silently, against its own rationale

**Location:** `_lym/discussion/decision-record.md` D13 and its Rationale.

**Issue:** D13's rationale says it refuses a retired key rather than ignoring it, so that a run pinned to one driver never silently runs another.
The refusal covers only `PrepareRunSettings` and the pair's local layer.
Every load drops a retired key from a hub base `loom.yaml` or `darn.yaml` without a word (`internal/configengine/doc.go:75-77`), and D13 says so itself: "every load still drops a hub base file's value until the reconcile prunes it".
So a hub that pinned loom runs to `driver_kind: llm` in its base `loom.yaml` silently runs `shed.yaml`'s driver, and the reconcile then deletes the tuned value.
The record names no bound and no way forward for that case.
This hub's own base `loom.yaml` tunes none of these keys, but other hubs are not checked.
Found also by the handler.

### [LOW] The required-heading check reads fenced lines

**Location:** `_lym/discussion/decision-record.md` D4, the claim "the discussion spec reads no fenced line".

**Issue:** Every section reader goes through `fencedLines` except one: `missingSections` (`internal/discussionparser/validate.go:113-128`) matches any line equal to a required heading, fenced lines included.
So an embedded body line `## Decisions` or `## Open risks` satisfies the section check.
A record that loses its own heading then passes the validate-only Darn-Write guard (D5).
It fails only later, when `decision add` refuses with `decisionWayNoHeading`.
D4's claim is false for this one reader.
Found also by the existing-paths lens.

### [LOW] Record-Write's write is not stated to be atomic

**Location:** `_lym/discussion/decision-record.md` D4, resume after a crash.

**Issue:** The "never overwrites one that exists" rule completes a pair after a crash that falls between two whole-file writes.
A crash during a write is different: it leaves a truncated `decision-record.md`.
The resume keeps that file, adds the support log and commits the pair.
Darn-Write's guard then fails on missing sections, and D6 forbids the writer to repair the record.
The repo already has an atomic write in `internal/fsx/fsx.go:53`.

### [LOW] D4 wrongly says the no-commit route re-captures the baseline

**Location:** `_lym/discussion/decision-record.md` D4, the in-flight Darn-Write bullet for a branch with no commits.

**Issue:** D4 says `goto --to Record-Write` then `resume` "captures the baseline again with the record".
It does not.
Drift-Baseline writes the scope and `baseline.md` only when either is missing, and a passed capture takes no new capture (`internal/driftengine/doc.go:67-68`).
The route still works, but the stated reason for it is false.
