**guard-reach findings**

1. **MEDIUM — Card 9 / D8: some row moves bypass the guard.** The pre-goto hook is the only place fixers are stopped. It covers `shedverbs.RunGoto`, which the cobra verb and `driverGoto` use. But `shedengine.Relaunch` also moves a halted run onto a target "as Goto does", and it never runs `Hooks.PreGoto`. Its callers are the tackler (`internal/sheddriver/tacklerconsume.go:56`) and the arbiter (`internal/shedarbiter/consume.go:59`), and both are part of the stop chain. One reachable case: Webster halts while a detached runner's card fixer is still in its fixer phase, and the tackler or arbiter relaunches onto another row. The fixer keeps editing under the next row, which breaks the acceptance criterion "a goto past a row with a live fixer leaves no fixer running". Card 9 neither lists nor guards this path. Evidence: `internal/shedengine/goto.go:190-193` (Relaunch doc) and the grep hits above.

2. **MEDIUM — Card 12 step 1: the "no kit" branch cannot stop the strand.** On a live `fixer.json` that the runner cannot attach to, the card says to "stop the strand through `Stop`". But `Stop` is a method of the kit's `Fixer`. When `cardFixer` turns the request down (the `card` key's `fixer` was cleared, the slug is now empty) or returns a load error, there is no kit and no `Stopper`. So the stop is unreachable on exactly the branch named for it. The record gets marked dead while the old fixer may still be editing, and the gate runs over its half-done edits, which D4 forbids. The card needs a stopper that does not depend on `handsOff`, for example a stop built from the worktree's reed geometry whatever the key's `fixer`. Evidence: Card 12's Intent, step 1 and the `newCardFixer` bullet.

3. **MEDIUM — Card 12 step 1: the attach wait is not a fixer phase, so the join exemption misses it.** While the runner waits on an earlier runner's live fixer before its own gate run, its phase stays `starting`. `joinable` relaxes the tree-identity rule only for the `fixing` phase. A repeated call from the caller during that wait sees the dirty paths the fixer is changing, so it fails the join and starts another run in the same key directory. That run finds the same live record and waits on it too. D4 says a call with the same key joins whatever tree it sees while a fixer works. The fix is to write `phaseFixing` before the step 1 wait as well. Evidence: Card 12 steps 1 and 3, and the `joinState.fixing` bullet. Tree-identity rule at `internal/gatecli/detachfront.go:320`.

4. **LOW — Card 12 step 3: race between the spawn and the phase write.** `fixing` is written after the spawn. `Starter.Start` returns once the provider is up, so the fixer can change dirty paths before the phase file says `fixing`. A caller's call in that window fails the join and starts a fresh run. The fix is to write the phase before the spawn. Evidence: Card 12 step 3 order: "spawns through the kit … it writes the phase `fixing`".

5. **MEDIUM — Card 6 step 1: the fixer entry's `Gate` never marks the record it waited on as terminal.** D2 says the record is marked terminal "by the fixer entry once its closure returns". Step 1 waits, re-runs the inner closure and returns without marking. The wait-only entries mark only on a failure. So after a darn `clean` entry waits and passes, and `verify` takes step 1, the record stays live. Every later evaluation in that visit takes step 1 again and never spawns a new fixer. A later restart's `Expired` also finds it live. The branch is reachable when the `Expired` probe errors, because a probe error counts as not expired (`internal/shuttleengine/wait.go:483-486`), or when the writer takes a turn after an attach. `TestWrapRowGate` has no row for the fixer entry's `Gate` with a live record, so this branch goes untested.

6. **LOW — Card 6 `Expired`: the cut-off is the wrap's build time, but D2 names the run's last attach.** `Expired` is true only for a live record whose `SpawnedAt` is before `WrapRowGate` was built. Take a record left live inside the same driver process, for example when the re-run's inner closure or a store write returns an error after the spawn, so the mark is never reached. If the run is then re-attached before the shed is rebuilt, `SpawnedAt` is after the build time, so `Expired` answers false. The idle writer then holds the run until the run deadline instead of finalizing at once. Evidence: Card 6's `Expired` bullet against D2's "saved before the run's last attach".
