### [BLOCKING] The two runs record contradicting decisions on who teaches the audit tool the per-card layout

**Location:** this run's decision record, Scope (Out: extending the audit tool of task `glyph-audit-tool` to the new layout), D4 (`## Start here` section in the per-card layout) and Open risks (the orch adds the layout to that entry, or files a note for it, when this task lands); `glyph-audit-tool`'s decision record, Constraints and D3, and its plan card `02-fork-records.md`.

**Issue:** `glyph-audit-tool` (running, Plan-Burler-Review, recipe row 9) records the constraint "A task that adds a pack layout adds its prompt marker row to `tools/forkaudit` in the same task", and its Open risks expect this task to add its marker row and a span source.
This run's decision record puts exactly that work out of scope and hands it to the orch after landing.
The two records contradict each other on the same work.

The contradiction is not only bookkeeping.
`forkaudit` checks its marker table in order, and its `file` row matches the `## Start here` heading (plan card `02-fork-records.md`).
This run's D4 keeps a closing `## Start here` section in the per-card prompt, so `forkaudit` would class every per-card fork as `file`.
Its D3 then keeps the prompt's arm on a trace disagreement: a `file` fork with trace `card` stays `file`, listed only as a disagreement.
The `trace:card` fallback that `glyph-audit-tool`'s Open risks rely on applies only to a fork whose prompt is `unknown`, which a per-card fork never is.
Until someone adds a marker row ahead of `file` (for example on `lyx loom card-pack`, which this run's Open risks name as the per-card tell), the per-card and file arms merge in the audit.
That defeats the measurement this board entry exists for: "so it can be measured against the current layout with the audit scripts".

The board entries settle neither side: `kickstart-per-card`'s entry asks for measurability, and `glyph-audit-tool`'s entry names this task as the next layout to compare but assigns the marker row to neither.
The run's parent must decide which run carries the marker row, or whether `glyph-audit-tool`'s constraint and file-arm marker change.
