### [BLOCKING] The segment-color decisions are carried by no card

**Location:** `_lyx/plan/00-overview.md` Card Index, cards 1–10; `_lyx/discussion/decision-record.md` "Added after Discussion (parent, 2026-10-08): The segment color goes through the send path after readiness" and "Burler: the merged raw /color typing is a blocking finding".

**Issue:**
The decision record settles that this task owns the `/color` fix.
Every path that types reed-view's `/color` into a session plays only after the provider is ready and goes through this task's send discipline (idle wait, settled box, confirmed landing).
A failed color send is logged and never fails the launch.
The two paths are named: `Start`'s `playInputs` of `ColorSequence` and `Runner.TypeColor`.
The decision also says why: three `loomcli` tmux-tier tests fail on the merged branch because the raw `/color` leaves text in the input box and the stricter readiness never sees the provider ready.

No card touches either path.
`grep -i color _lyx/plan/` finds only two unrelated `playInputs` mentions in the overview's `send-context` decision and card 4.
In the working tree, `internal/shuttleengine/run.go` (`Runner.start`, after `awaitStartup`) still calls `playInputs(r.reed, strand.GUID, r.engine.ColorSequence(strand.Color))`, and `internal/shuttleengine/session.go` (`Runner.TypeColor`) still ends in `playInputs(r.reed, guid, r.engine.ColorSequence(color))`.
Cards 3 and 4 make the readiness guard and the send strict without moving the color typing, so a plan executed as written reproduces the failure the decision names.
`doc.go`'s paragraph on `Engine.ColorSequence` (start plays it after startup confirms the provider ready) also goes unmentioned.
No acceptance-criterion-shaped row covers it either: the plan names none of the three tests the decision requires to pass.

**Fix:**
Add a card, after card 4 (it needs card 3's idle wait and card 4's settle and confirm) and before or after card 5, that:

- Edits `internal/shuttleengine#Runner.start` and `internal/shuttleengine#Runner.TypeColor` to send the provider's color command through `sendVerified` with a `sendContext`, so it waits for idle, settles and confirms landing.
- Logs a failed color send at Warn and never fails the launch, with the Intent stating that bound (a color send that fails or times out can only leave the pane uncolored; it types nothing else and ends nothing).
- Edits `doc.go`'s color paragraph and the existing tests that cover the color play in `startup_test.go` / `session_test.go` (extend, not new tests), adding a row for a failed color send that does not fail the launch.
- Carries a `**Verify:**` running the tmux tier for the named packages, `go test -tags tmux ./internal/loomcli/... ./internal/shuttleengine/...`, since the plan-level `## verify:` only compiles that tier and the decision names `TestIntegrationDriverBootstrap_ReturnsWithoutWaitingOnTheDriver`, `TestSmokeDriverStrand_ReentrantAcrossThreeBootstraps` and `TestSmokeStart_NeverAttachesAndAddsNoOperatorStrand` as the proof.

### [MEDIUM] Card 4's empty-box shortcut also fires on the paths where no Enter was sent

**Location:** `_lyx/plan/04-send-settles-and-confirms.md`, Intent: "On every `ErrSubmissionNotLanded` from the box path (unsettled, never confirmed, never appeared), `sendVerified` first calls `clearUnlandedText`: it reads the box once; an empty box means the submission landed late, and the send returns nil instead of failing (D4's first catch)."

**Issue:**
An empty box can only mean "landed late" after an Enter has gone out.
Two of the three listed causes have sent none: a box that never settled gets no Enter by D2, and a text that never appeared in the pane is detected before `awaitSettledBox` runs.
For those, an empty box means the typed text was swallowed or lost, not submitted.
Under the card's wording `sendVerified` returns nil, and start (D4) then proceeds with an agent that never received its prompt, which is the failure class this task removes.
It also contradicts the acceptance criterion "A sent text that never appears in the pane fails with `ErrSubmissionNotLanded`", and D3, which sends no clear key into a box reading empty but ties the success to a D4 box reading after the confirm path.
The decision record states the late-landing catch only for the unconfirmed-after-Enter case ("A prompt that landed late is caught twice").

**Fix:**
Narrow the sentence: the empty-box success applies only to the never-confirmed cause, where an Enter was sent.
For an unsettled box and a text that never appeared, `clearUnlandedText` may still clear the send's own text, but an empty reading returns `ErrSubmissionNotLanded`.
Add the matching rows to the extended `TestRun_Send_ConfirmsSubmission` and `TestRun_Send_DeliveryVerification` tables (a never-appeared text over an empty box fails; an unsettled box reading empty at the end fails).
