### [MEDIUM] `lyx fabric code` sweeps the live board into its commit, unlocked

**Location:** internal/fabriccli/code.go:51

**Issue:** `runCode` writes `.lyx-code` and then calls `fabricengine.NewBolt(boardDir).Commit(...)`.
`Bolt.Commit` is `commitWeftAt`, which stages and commits *every* change in `_board`.
`CloneAndWire` can do that safely because the hub it commits on was created a moment earlier and nothing else writes to it.
`lyx fabric code` runs on a live hub instead, where `boardengine` writes tracker files under `board.lock` and commits them through its own `Sync`.
A board write that is pending or half-written when the verb runs is swept into a commit titled "fabric code: record the repo's short code".
It is also committed without the board write lock, which `fabricengine.BoardWriteLockFile`'s own doc says every board writer outside `boardengine` must take (`CommitSeededStencils` is the precedent).
The Fabric Git Invariant also asks every weft-commit caller for a positive file list through `ScopedPathspec`, which this commit does not use.

**Fix:** Add a `fabricengine` function that records the code on a live hub the way `CommitSeededStencils` commits stencils.
It takes `BoardWriteLockPath(hub)`, writes the file, and stages and commits only `.lyx-code` through a positive pathspec, recording the mutations.
`runCode` calls it and then pushes through `Bolt.Push`.

### [MEDIUM] The tmux server inherits the spawner's agent-name env

**Location:** internal/reedengine/lifecycle.go:327

**Issue:** The per-hub tmux server is spawned with `CleanClaudeEnv(os.Environ())` plus `stripTraceID`, which still leaves `LYX_STRAND_NAME` and `LYX_PARENT` in place.
When the server is first booted from inside a strand, its global environment keeps that strand's name and parent.
That happens, for example, when an orch or driver strand runs `lyx loom start`, `lyx batten run` or `lyx reed up` after a server restart.
Every pane the server later creates inherits those values.
`nameExports` overrides `LYX_STRAND_NAME` for every formed name, but it exports `LYX_PARENT` only when a parent is told.
A strand in the prime, or in a worktree whose seed records no parent, therefore sees the booting strand's `LYX_PARENT`.
The ly-drive skill sends its escalations to that wrong session.
Selvage and every non-strand pane also carry a wrong `LYX_STRAND_NAME`.
A `batten run` or `loom start` typed in such a pane would then record the wrong parent in its seed.

**Fix:** Strip `agentname.StrandNameEnv` and `agentname.ParentEnv` from the server spawn env, beside `stripTraceID` and for the same reason: the server is a long-lived singleton, not a child of the invocation that happened to boot it.
Pin it with a unit test on the stripping helper.

### [MEDIUM] hubgeom tells a task worktree a prime-shaped geometry when PrimeName fails

**Location:** internal/hubgeom/hubgeom.go:29

**Issue:** Card 6 says "A `PrimeName` failure is the function's only error".
The implementation logs a warning instead, substitutes `prime = l.WorktreeName` and returns a nil error, so the error return is dead.
In a task worktree where `git worktree list` fails, reed is told an empty `NameSlug` and an empty `ParentName`.
Every strand spawned there is then named `<code>:<role>`, so names like `ly:driver` collide with the prime's own in `lyx reed list` and in `LYX_STRAND_NAME`.
Escalation addressing would then reach the wrong session, and the strand would get no `LYX_PARENT`.
The stated reason is that Tier 1 wiring tests pass fictional, git-less locations.
That is a test-fixture convenience bought with silently wrong production names.

**Fix:** Return the `PrimeName` error as the card specifies, so each caller fails on the path it already uses for a failing geometry.
Fix whichever Tier 1 tests relied on the fallback.

### [LOW] `--if-absent` misses a legacy exact name

**Location:** internal/reedengine/strand.go:249

**Issue:** `classifyIfAbsent` compares `s.Name == name` against the full name `validateNaming` resolves.
The VS Code `folderOpen` chain runs `lyx reed add --if-absent --name claude` (`internal/vscode/config.go`).
In a worktree whose strand was recorded before this task as exactly `claude`, the first reopen after the deploy finds no match and adds a second `claude` pane beside the live one.
That is exactly the duplicate `--if-absent` exists to prevent.
The plan's shared decision says every by-name lookup accepts a legacy exact name, but this lookup does not.

**Fix:** Also match `s.Name == spec.NameOverride` when the override carries no `:`, so a legacy exact name is found as `agentname.Matches` would find it.
Add a test with a legacy-named strand.
