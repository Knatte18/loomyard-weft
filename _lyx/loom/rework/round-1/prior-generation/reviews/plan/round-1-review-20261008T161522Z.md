### [BLOCKING] The /color decisions are carried by no card

**Location:** `_lyx/plan/00-overview.md` Card Index; `_lyx/discussion/decision-record.md` "The segment color goes through the send path after readiness" and "Burler: the merged raw /color typing is a blocking finding".
**Issue:** The decision record's Decisions section ends with two entries that make this task own the `/color` fix after the merge with reed-view.
Every path that types `/color` into a session, namely `Runner.start`'s `playInputs(r.reed, strand.GUID, r.engine.ColorSequence(strand.Color))` after `awaitStartup` and `Runner.TypeColor` in `session.go`, must play only after the provider is ready and go through the new send discipline (idle wait, settled box, confirmed landing).
A failed color send is logged and never fails the launch.
The record also names three loomcli tmux-tier tests (`TestIntegrationDriverBootstrap_ReturnsWithoutWaitingOnTheDriver`, `TestSmokeDriverStrand_ReentrantAcrossThreeBootstraps`, `TestSmokeStart_NeverAttachesAndAddsNoOperatorStrand`) that fail until it is done.
I searched `_lyx/plan` for `color` and found no hit, and no card targets `Runner.start`'s color block or `Runner.TypeColor`.
The ten cards were written (mtime 13:43 to 13:58) before these entries (decision record, 17:46), and the plan was not extended.
Without the fix, card 3's strict readiness makes `Runner.start`'s raw `/color` leave text in the input box, and the very wiring the record says blocks Publish stays broken.
**Fix:** Add a card after card 4, since it consumes the verified send path (`sendVerified` with its `sendContext`), and place it before card 5 or after it so long as card 5's start flow is not re-ordered under it.
Its targets are `internal/shuttleengine#Runner.start` (the color block) and `internal/shuttleengine#Runner.TypeColor`, with `internal/shuttleengine/doc.go`'s color paragraph and the start tests in `startup_test.go`.
Its `Intent` states that the color goes through the verified send after readiness, that a failure is a Warn and never fails the launch, and what bounds the new wait (`send_ready_timeout_s`).
`ColorByCaller` callers (orch watcher, loom driver) reach it through `Runner.TypeColor`.
The `## verify:` section can stay as the template prescribes, because the `tmux` tier named in the record runs at Publish.

### [BLOCKING] An empty box reads as landed for every failure cause, including text that never appeared

**Location:** `_lyx/plan/04-send-settles-and-confirms.md`, the paragraph "On every `ErrSubmissionNotLanded` from the box path (unsettled, never confirmed, never appeared), `sendVerified` first calls `clearUnlandedText` ... an empty box means the submission landed late, and the send returns nil instead of failing".
**Issue:** The decision record gives the empty-box-means-landed inference only for a submission that was sent and is pending (D4, "the box reading D3 takes before its clear shows an empty box, so the send succeeds").
D3 itself says only that a box reading empty gets no clear key.
Card 4 applies the inference to all three causes.
After "never appeared" (the TUI swallowed the input) the box is empty because nothing was typed, so `sendVerified` returns nil for an undelivered text.
After "unsettled" no Enter was ever sent, so an empty box means the typed text vanished, not that it landed.
This contradicts D2 and the acceptance criterion "A sent text that never appears in the pane fails with `ErrSubmissionNotLanded`", and it turns the only real engine (Claude, which has `InputBoxReader` and the idle reading) into a silent success.
The consequence is a gate re-prompt or start-time prompt counted as delivered that the agent never received; start then returns a run handle that waits on a prompt-less agent until its deadline.
The card's own tests assert `errors.Is(err, ErrSubmissionNotLanded)` for never-appeared rows only on engines without `InputBoxReader`, so no row would catch it.
**Fix:** Restrict the empty-box-means-landed return to the cause where an Enter has been sent and the box is still unconfirmed at the window's close (the "never confirmed" path).
For "never appeared" and "unsettled", an empty reading returns the `ErrSubmissionNotLanded` error with the pane tail and sends no clear key.
Add rows to the card's table for an empty box after each of those two causes expecting the error.

### [MEDIUM] Status-cap teardown rests on a false premise and contradicts a documented residual

**Location:** `_lyx/plan/05-start-send-teardown.md`, the paragraphs on `awaitStartup`'s three status-cap exits and the `Bound`.
**Issue:** Card 5 makes `errStrandNotTracked`, `errStrandPaneBindingCleared` and the repeated reed-status failure call `abandonStartup(OutcomeDied, ...)`, so they kill the strand, finalize `died` and wrap `ErrNotStarted`, which `shedtransient` maps to the agent-start transient class.
Its `Bound` says these exits happen "only before the provider was seen ready, so no prompt was delivered".
That does not hold: `loadSkillsThenPrompt` runs only for a launch that deferred its prompt (`launch.PromptLine != ""`), so every other launch carries its prompt on the launch command line and the agent is already working while reed's status fails.
The base code states this deliberately: `awaitStartup`'s doc comment says a status-cap failure "tears nothing down because it says nothing about the agent", and `internal/loomcli/start.go`'s `startLLMDriverArm` comment records as an accepted residual that the strand is left in place "because reed being unable to answer says nothing about the agent, so tearing the strand down could kill a working driver".
Card 5 reverses that design, does not edit the `loomcli` comment (now false), and widens `TransientAgentStart` to a case outside D4's bound ("The widened class still excludes an agent that took its prompt and then died").
D4's sentence "every other start failure past `AddStrand`" can be read to include these exits, but the record never weighed killing a possibly working agent on a reed outage, so the plan has to either make that choice explicitly or leave the exits out.
**Fix:** Decide one of two ways and say which in the card.
Either keep the three status-cap exits as today (the record stays `running` over a live strand, which is the documented residual) and limit the teardown to the send, prompt-offset persist and skill-loader failures D4 names, or keep the teardown but correct the `Bound` premise, state what bounds a kill of a working agent, and add the stale `startLLMDriverArm` comment and `awaitStartup`'s return-mapping to the edit list.

### [LOW] The record lock list omits one in-Run save

**Location:** `_lyx/plan/07-shuttle-stop-verb.md`, the paragraph beginning "`Run` gains a record mutex and a stop mark".
**Issue:** The card says the lock guards "every save of `run.state`", all through `saveState`, and lists `finalize`, `notifyHeld` and `checkLivenessTick`.
`loadSkillsThenPrompt` also calls `saveRunState(run.runDir, run.state)` for the prompt offset; card 5 touches that method but card 7 does not.
The save runs before the handle is issued, so it cannot race `Stop`, but then the card's "every save" is untrue as written, and the decision's "every saveRunState call on run.state from the Run" has an unlisted site.
**Fix:** Either add `internal/shuttleengine#Run.loadSkillsThenPrompt` to the card's `Edit` list so its save goes through `saveState`, or reword "every save" to "every save made after the handle is issued" and name the pre-handle saves as exempt.
