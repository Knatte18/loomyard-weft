# tokencount: read each message's usage from its last transcript line

tokencount under-counted sub-agent (fork) output tokens.
Claude Code can record one API message on several transcript lines, and in a sub-agent transcript the earlier lines carry a partial `output_tokens` (6 on a thinking block against 4,546 on the message's final line).
tokencount kept the first line per message id, so fork costs came out low; main-session figures were unaffected because their lines carry the final usage.

The run counter (`countFile`) and the orch counter (`readTranscript`) now gather a transcript's usage lines and keep each message id's last line, in the order the ids first appear, through one shared helper, `lastLinePerMessage`.
Each id still counts once per run across transcripts, so a fork's repeat of its parent's context is still skipped.
Only the run counter's dropped earlier lines add to the report's count of repeated transcript lines skipped; the orch counter does not report its drops.
An orch message's timestamp, which decides its window and charge, is now its last line's.

`TestCountRun` gains a fork message whose first line carries a partial output count; the fork's tally must hold the last line's figure.
The package doc in `tools/tokencount/main.go` states the last-line rule.

Cost figures already recorded with the old count, such as the twill fork-timing benches and `docs/research/token-usage-by-role.md`, are measurement reports of their run and are not rewritten here; their fork costs are low until re-measured.
