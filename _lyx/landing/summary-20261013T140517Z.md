# Webster fork prompt: kick-start pack and its read line last

The implementer fork's kick-start pack used to sit mid-prompt, at the end of the cards section, while its one-turn read instruction stood in the FRESH-READ rule at the top of a prompt of about 300 lines.
The glyph audit found only about half of the pack-on forks reading in parallel in their first work turn.
The end of a prompt is what an agent acts on first, so the pack and its read instruction now come at the end.

## What changes

- The `kickstart_pack` marker moved from the end of the cards section to the very end of `webster-body-implementer.md`, after the batch-report section.
  The pack section is filled inline there, so it is the prompt's last section.
- The pack section opens with the line "Read all of this in one turn, in parallel, before any edit", followed by the spans, whole-file and unresolved-glyph reads that line covers, then one subsection per card as before.
- The batch-report section still names the report as the fork's last action.
- The pack-on FRESH-READ rule points at the pack section instead of carrying the read instruction.
- A batch where no card has a resolved or unresolved entry now counts as no pack: the prompt renders as with the switch off, and the begin-batch trace line logs `kickstart_pack=empty`.
  Before, such a batch got a pack section saying each card named no member glyph.

Without a pack (switch off, language `none`, empty pack) the prompt's bytes are unchanged, and the recovery prompt never takes a pack.

## Docs and tests

`internal/websterengine/doc.go`'s kick-start pack section describes the inline layout and the `empty` log state.
The stencil claims and marker tests pin the new layout: the marker ends the body, and FRESH-READ no longer carries the read instruction.
The render tests check that a prompt with a pack ends with the pack section.
`TestBeginBatch_KickstartPack` covers the empty-pack case.

## Measure afterwards

The glyph audit's scripts can re-run unchanged on runs after this lands, comparing the share of forks with three or more parallel reads in the first work turn and the exploration calls per card.
